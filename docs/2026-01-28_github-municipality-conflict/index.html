GitHubと自治体業務の相性：なぜ「構造的に」噛み合わないのか？

  • #GitHub
  • #自治体
  • #業務改善
  • #組織文化
  • #情報セキュリティ

エンジニアにとってGitHubは「なくてはならないインフラ」ですが、自治体業務においては「導入が極めて難しいツール」の一つです。

これは単に職員がITに不慣れだからではありません。GitHubが前提とする「分散管理」の思想と、自治体が守るべき「中央統制」の思想が、構造的に対立しているからです。

1. 構造的な衝突：ローカル vs 中央

Gitの基本は「ローカル（手元のPC）に全てをコピーし、手元で作業して、最後に送信（Push）する」ことです。しかし、これが自治体のセキュリティポリシーと真っ向から衝突します。

ローカル至上主義

手元に全履歴をコピー。
試行錯誤は個人の自由。

VS
端末信用ゼロ主義

端末にデータを残すな。
誰がいつ何をしたか監視せよ。

作業プロセスの比較

🏢
従来のWebシステム（常にサーバで処理・ログ残る）
🐙
Git（Pushするまで手元作業はブラックボックス）

※「手元で何が起きているか見えない時間」が許されない

2. 「決裁文化」との不整合

GitHubの強みである「途中経過の記録（Commit）」も、自治体の「決裁文化」とは相性が悪い要素です。

観点 GitHubの価値観 自治体の価値観
途中経過 価値あり
試行錯誤の履歴を残す		 ノイズ
決裁前の文書は「非公式」
変更管理 差分（Diff）で見る 版数（第◯版）で見る
説明責任 「コードが全て」 「誰が承認したか」

監査で「このCommitは正式な文書ですか？」と問われたとき、開発途中（WIP）のログが残っていることは、説明コストを増大させるリスクになります。

3. 物理的な壁：三層分離

さらに深刻なのがネットワークの問題です。多くの自治体では、業務端末（LGWAN系）からインターネットへの直接接続が禁止されています。

💻 業務端末
(LGWAN)
🚧 🚧 🚧
☁️ GitHub
(Internet)

「git cloneできない」「sshが通らない」が日常。
使うには専用のインターネット端末が必要になる。

4. それでも使うなら：「思想の翻訳」が必要

自治体でGit的な管理を導入するには、GitHubの思想をそのまま持ち込むのではなく、自治体の文脈に「翻訳」して運用する必要があります。

💡 自治体向け「Git運用」の翻訳例
  • ローカル作業を禁止する：
    PCにCloneせず、ブラウザ上のエディタ（GitHub Codespaces等）だけで完結させる。「端末にデータを残さない」原則を守る。
  • 人は「入力者」に徹する：
    直接Commitするのではなく、フォーム入力やIssue起票を行い、CI/CD（自動化）が代わりにCommitする。「システムによる記録」にする。
  • Mainブランチ＝決裁済み：
    Pull Requestのマージを「承認行為」と定義し、Mainブランチのみを「公文書」として扱う。

まとめ

GitHubと自治体業務の相性が悪いのは、ツールの良し悪しではなく「自由（エンジニア）」と「統制（行政）」という正反対の目的を最大化しようとしているからです。

導入するなら、「エンジニアのように自由に使ってもらう」のではなく、「裏側でGitが動いているが、職員はそれを意識しない（Web画面で完結する）」仕組みを作ることが、最も現実的な解となるでしょう。
